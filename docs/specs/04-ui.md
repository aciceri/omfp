# 04 — UI (TypeScript)

The UI is a TypeScript web app (D-18): React 19 with React Aria Components (S-11), styled by our own token CSS,
bundled and tested with Bun, in the `ui/` workspace. The same bundle runs in the browser, served by the daemon
(DMN-008), and from M7 in the Tauri desktop window: same components, same state handling.

## Platforms

| | Web | Desktop (M7) |
| --- | --- | --- |

### macOS (M11)

The desktop window on macOS is the same Tauri 2 window on the system's WKWebView (S-15); the daemon's tray is a menu
bar item (DMN-171). The platform differences:

| ID | Requirement |
| --- | --- |
| UI-250 | (M11) **Window storage on macOS**: WKWebView ignores a data directory, so the window MUST take a `WKWebsiteDataStore` identifier per data directory (UI-005): 16 random bytes made on first use and kept in `<data dir>/webview/store-id` (replaced when not 16 bytes), so two daemons never share the window's `localStorage` (macOS 14 or later). Before the app exits, the window MUST wait (at most 5 s) until WebKit has committed that `localStorage`: WebKit's network process keeps the page's writes in a SQLite transaction it commits 500 ms after the first one and ends with the app, which lost the last writes, e.g. a file tab closed just before the window, which then reopened at the next start. The wait takes and releases the write lock of each origin's `localstorage.sqlite3` in the store's directory (`~/Library/WebKit/dev.omfp.desktop/WebsiteDataStore/<id as a UUID>/Origins/…/LocalStorage/`, under the user's home whatever `HOME` says). |
| UI-251 | (M11) **Microphone on macOS**: the binary MUST embed an Info.plist (`__TEXT,__info_plist`: bundle id `dev.omfp.desktop`, `NSMicrophoneUsageDescription`, `LSMinimumSystemVersion` 14.0), without which WKWebView hides `navigator.mediaDevices`; the window MUST grant WKWebView's microphone requests (unhandled, WebKit asks on every page load), so macOS asks the user once per app (TCC: the app's signature, so again after a rebuild while the bundle is ad-hoc signed, ENV-041). WKWebView has WebRTC, so live voice takes `thread.live_connect` there like a browser (UI-188). |
| UI-252 | (M11) **Notifications on macOS**: WKWebView denies web notifications, and the window has no IPC, so the window MUST give the page its own `Notification` (an initialization script, before the page's scripts): `permission` `granted`, and each `new Notification(title, { body, tag })` a navigation of a hidden frame to `omfp-notify:?title=…&body=…&tag=…`, which the window cancels and posts to macOS's notification center as `dev.omfp.desktop` (`NSUserNotificationCenter`: its successor needs an app bundle around the running executable; a notification with the same tag replaces the last one). The page's routing is unchanged (UI-096, UI-192: a system notification while the window has no focus). macOS asks once whether `omfp` may show notifications (until allowed, they only reach the Notification Center's storage); a click does not select the thread (no delegate without `unsafe`). Linux keeps WebKitGTK's own notifications. |
| UI-253 | (M11) **Color scheme on macOS**: the window MUST follow the system appearance through AppKit (WKWebView maps the window's effective appearance to `prefers-color-scheme`); the settings-portal follower of UI-195 is Linux only. |
| UI-254 | (M11) **Menu bar item**: on macOS the tray of UI-217..UI-219 MUST be an `NSStatusItem` with the same menu model: a click opens the menu (the macOS convention; no left-click New window), labels without the `_` doubling, the tooltip the status line; the idle icon is a template image (the π's alpha, tinted by macOS for a light or dark menu bar), running and needs-you keep their coloured dots. **Open in browser** runs `/usr/bin/open <url#token>`. |
| UI-280 | (M11) **Key chips on macOS**: where `navigator.platform` starts with `Mac` (browsers and the desktop window's WKWebView), the key chips of UI-148 and the `:help` panel (UI-198) MUST label the Alt modifier `opt` (`opt+a`, `opt+enter`), the macOS key's name; the bindings stay `Alt-…` and every other label (and Linux) is unchanged. |
| UI-281 | (M11) **Zoom on macOS**: the desktop window's View menu MUST hold Actual Size (Cmd-0), Zoom In (Cmd-=) and Zoom Out (Cmd--) atop Tauri's default items, which set the webview's page zoom through the browsers' steps (50, 67, 75, 80, 90, 100, 110, 125, 150, 175, 200, 250, 300 %; the ends stay, a level between two steps goes to the next). No key of the keymap uses Cmd. Linux has no such menu: Tauri's zoom hotkeys are a page script calling the window over IPC, which the window does not have (S-04), and WebKitGTK windows have no menu; its window zooms on the page's keys and wheel instead (UI-283). |
| UI-282 | (M11) **New window on macOS**: the desktop window's File menu MUST start with New Window (Cmd-N), which starts one more `omfp desktop` detached — `--data-dir` of this window, `--connect` and `--token` when this window got them, not its `--thread` — like the menu bar's New window (UI-218, UI-254). Linux has no such key: without a menu the page would have to send it, and Ctrl-n is the file editor's vim key (UI-111). |

## State and code structure

The UI is a Bun workspace of small packages. The protocol client has no UI dependency, so it is tested against a real
daemon and can serve other clients (scripts, agents, the desktop shell):

```text
ui/packages/
  protocol/      @omfp/protocol: protocol types and method table generated from the daemon's JSON Schemas
                 (`just gen-ts`), envelope, topics
  core/          @omfp/core: the omfp-core reducer ported to TypeScript, checked against the Rust reducer's golden
                 states (D-04)
  client/        @omfp/client: transport (WebSocket); session (hello, request/response correlation, subscriptions
                 with {epoch, seq}, reconnect with backoff, resubscribe, resync); model (connection status, index
                 with repositories, workspaces, threads and theme, per-thread ThreadState, change notifications)
  kit/           @omfp/kit: React Aria Components wrappers styled by token CSS (tokens.css, kit.css)
  app/           @omfp/app: the web app; build.ts makes the release bundle in dist/ (with the import map that
                 widgets resolve `react`, `omfp/sdk` and `omfp/kit` through, AGT-012)
    src/sdk/       the widget SDK, `omfp/sdk` (AGT-016): host, frame store (one snapshot per animation frame),
                   window store (window-local state), commands, hooks over the client model, widget hooks
    src/vm/        pure view-model functions: ThreadState / DTOs → display data (unit tested, no DOM)
    src/widgets/   the built-in `omfp:*` widgets (thin: render vm output, call the SDK), each folder written like an
                   agent widget so it can be copied (AGT-021)
    src/frame/     the frame outside the view: left column, connection banner, the mode line with the view tabs,
                   `:` command line and `:widget add`, safety net for pending interactions, notifications, live region
    src/view/      views: layout tree (`row`/`col`/`tabs`/`stack` of widget refs with props, the `views.json` shape
                   of 08) rendered from the widget registry (see UI-024), the widget loader and `:widget add`'s edit
    src/keymap/    keymap as data: key sequence → command id, per mode
    src/theme/     built-in themes (data-theme), user theme from the daemon, color scheme and density
    src/strings/   all UI text
```

| ID | Requirement |
| --- | --- |
| UI-010 | Thread state MUST come only from the `omfp-core` reducer (ARC-006). UI-only state (scroll position, expanded cards, composer draft) lives beside it and is never sent to the daemon. |
| UI-011 | Display logic (grouping, labels, status badges, tool-card summaries, diff stats) MUST live in `ui/packages/app/src/vm/` as pure TypeScript functions, so it can be tested without a DOM (TDD at unit level). |
| UI-012 | Model updates from streaming events MUST be coalesced to at most one render per animation frame. |
| UI-335 | **Recent threads stay followed**: a `thread/<id>` topic MUST stay subscribed after no widget shows it any more, for the most recently hidden threads (`[ui] recent_threads`, default 20, `DEFAULT_RECENT_THREADS`, UI-996; the least recently shown goes first, and a kept thread deleted from the index is released), kept without watching the thread (UI-997), so switching back to one of them sends no `subscribe` and renders its kept, live-updated state at once instead of waiting for a new snapshot (`TopicRefs`, `ui/packages/app/src/sdk/host.tsx`). Measured by TST-100 with 10,000 messages: switching back took 168–179 ms to the DOM (a 5.5 MB snapshot), 22–24 ms after. Any other topic MUST stay subscribed, its state in the model, when a widget follows it again in the same task as the last one released it: a tab or kept view hidden (`<Activity>`, UI-390, UI-400) while another one following the same topic shows, as `omfp:changes` beside `omfp:workspace` (both `workspace/<id>`), whose files otherwise flashed `Loading…` until a new snapshot; else it is unsubscribed in a microtask. |
| UI-996 | **How many threads a window keeps**: the bound of UI-335 MUST be `[ui] recent_threads` (0–100, or `"all"`; default 20; `settings.set`, `:set recent_threads=<n>` or `:set recent_threads=all`, UI-097), applied live: lowering it releases the oldest kept threads at once, `0` keeps none, and `"all"` releases none, so every thread shown in the window stays kept until the window closes or reloads (a thread deleted from the index is still released). The cost is the window's memory, not omp's (UI-997): each kept thread's whole state stays in the window's model, on the order of its snapshot (a 10,000-message thread's is 5.5 MB of JSON, TST-100), so long threads add up per window; with `"all"` a window that went through hundreds of long threads can hold gigabytes, too much for a phone's browser, which may reload or kill the tab. |
| UI-997 | **Kept threads are not watched**: when no widget shows a thread any more and the window keeps it (UI-335), the window MUST switch its live subscription to kept with `watch { topic, watch: false }` (PRT-223), without unsubscribing nor resubscribing, so the kept thread holds no omp (the idle reaper stops it after `idle_timeout`, DMN-356) and the window is not the one the user last used on it (DMN-357); the window still follows the topic, keeps the transcript and shows the stopped state. When a widget shows the thread again the window sends `watch { topic, watch: true }` on the same subscription (no new snapshot). The client keeps each topic's flag: a resubscription after a reconnect or a resync sends `watch: false` for a kept thread (PRT-222). |
| UI-998 | **Showing a thread starts no omp**: nothing a window issues because a thread is shown, kept (UI-335) or its composer focused may start the thread's omp (DMN-070): the header, tree and background read omp only while it runs (UI-030, UI-083, UI-081) and the composer asks `thread.commands`, which never starts omp (DMN-358), only once its draft starts with `/` (UI-060). A thread without a running omp offers the usable models of `auth.models` (a short-lived omp each time, PRT-140), asked once per window and login state — this window's logins and logouts (UI-385) and the daemon's count of usable models (PRT-141) — not for every thread shown. omp starts when the user sends something (a message, a `/` command, a model or thinking change, Restart) or asks for what only omp answers (the tree's refresh, a subagent's transcript, Fork from a message). |

## Layout

The left column lists workspaces and, inside each, its threads; the selected thread's workspace is the current one.
The left column belongs to the frame; everything right of it is the current workspace's view (widgets, 08: its
`views.json`, else the default view): the conversation and, beside it, widgets about the current workspace.

```text
┌────────────────────┬───────────────────────────────────────────┬────────────────┐
│ / filter threads   │ Thread header: title · workspace chip     │ omfp:workspace │
│ + workspace        │ · model · thinking · context % · state    │  checkout-v2   │
│ ▾ checkout-v2      │───────────────────────────────────────────│  ↪ frontend    │
│   ● implement      │ Transcript (virtualized)                  │  ⑂ fe-v2       │
│   ◐ review         │   user / assistant / tool cards / notices │  ⬇ backend     │
│   + thread         │   pending interactions (approval, ask)    │  + repository  │
│ ▾ scratch          │───────────────────────────────────────────│                │
│   ! questions      │ Queue chips · Composer (/ commands, imgs) │  (more widgets)│
│   + thread         │                                           │                │
└────────────────────┴───────────────────────────────────────────┴────────────────┘
```

## Files (M5c)

A file viewer for quick edits (00: not an IDE), built on CodeMirror 6 (spike S-13): the built-in `omfp:file` widget,
opened from paths anywhere in the window. The editor, vim, the merge view and each language are chunks of the bundle
loaded on first use.

An explicit `:open <filename>[:<line>[:<column>]]` / `file.open` argument MUST accept arbitrary filenames, including
bare media names, unknown extensions and spaces, independently of conservative inline prose path detection.
For example, `:open tone.wav` resolves the unique `media/tone.wav`, offers the existing picker for ambiguous
basenames, and shows the normal missing-file result if none exists. With no argument, focused-path behavior stays.

## Copying and exporting a conversation (M17)

omp's TUI has `/copy` and `/export` (an HTML file of the session). omfp renders the conversation itself, in the window,
from the thread's reducer state: no omp process is needed, so a stopped thread's conversation copies too. omp's
`export_html` RPC command is not used: it needs a running omp and writes the file on omp's host, out of the browser's
reach. Only Markdown is exported: an HTML file would need the transcript's renderer and styles bundled into it.

| ID | Requirement |
| --- | --- |
| UI-790 | **`:copy`** (command `thread.copy`, no default key) MUST copy the selected thread's conversation to the clipboard as Markdown (UI-792); in the transcript scope with a message focused (`j`/`k`, any message row: user, assistant, record or the streaming reply) only that message, its blocks without the heading. The result is the success toast `Copied the conversation` or `Copied the message` (UI-520); a refused or missing clipboard is an error toast. A thread whose state the window does not hold yet is followed (`thread/<id>`) until its snapshot arrives; the clipboard write still starts within the user's gesture (Safari refuses it later): a `ClipboardItem` whose text resolves once the Markdown is ready, else `writeText` once it is. |
| UI-791 | **`:export`** (command `thread.export`, no default key) MUST save the conversation's Markdown (UI-792) as a file named after the thread's title (its letters and digits in lower case joined by `-`, at most 80 characters, `conversation` without any, then `.md`) through a browser download of a `blob:` URL, then show `Exported “<file>”` (UI-520). The desktop window saves the downloads of its daemon's page's own `blob:` URLs, and only those, in the user's Downloads folder (Tauri numbers the name rather than replacing a file). |
| UI-792 | **The Markdown** MUST be `# <title>`, then each message row of the transcript in order under `## You` (`## You (steering)` for a steer), `## Assistant` or `## <record kind>`, an assistant message continuing its turn without its own heading (UI-470): text as written (blank lines around it dropped, the first line's indentation kept); thinking left out; an image as `*[image: <mime type>]*`; a tool call as ``**Tool `<name>`** <summary> (<status>[, <duration>])`` followed by its result's text in a fenced code block (the result's images as `[image]`); a record as its one-line summary; a failed reply's error as a `> **Error:** …` quote. omp's bookkeeping rows and the notices are left out; the reply being streamed is there as it stands. |
| UI-793 | The header's `⋯` popover MUST offer *Copy conversation* and *Export*, which copy and export the whole conversation like `:copy` and `:export` and close the popover. |

## Compacting the context (M17)

omp's TUI compacts on demand with `/compact [mode] [focus]`. Over RPC, omp 18.22.0's `compact` command takes only
`customInstructions` (the focus of the summary, `thread.compact`'s `instructions`); its modes (`soft`, `remote`,
`snapcompact`, `compact-modes.ts`) reach omp only through its `/compact` builtin sent as a prompt, which reports its
outcome in the transcript. omp itself aborts a running turn to compact and resumes it after the summary; the window
refuses instead, so a compaction never cuts a turn the user did not stop.

| ID | Requirement |
| --- | --- |
| UI-910 | **`:compact [focus…]`** (command `thread.compact`, no default key, offered for a selected thread that is not archived) MUST call `thread.compact` on the selected thread with the words after it, trimmed, as `instructions` (none when blank). While the thread works (its summary not `settled`) it MUST call nothing and show the error toast `The thread is working: compact it once its turn ends (Abort ends it now)`. |
| UI-911 | **The result**: once `thread.compact` answers, the success toast `Compacted the context (it held <n> tokens)` (UI-520; `<n>` omp's `tokensBefore` as a compact number, the plain `Compacted the context` without a positive one); omp's refusal (`Nothing to compact (session too small)`, `Already compacted`, `Compaction already in progress`, …) is an error toast. The transcript shows omp's `manual_compaction_start`/`manual_compaction_end` as the compaction notices of UI-043; a compaction omp skipped (`skipped`, its reason in `errorMessage`) is the info row `Compaction skipped: <reason>`, not a failure, and the `Compaction failed: <reason>` output omp's `/compact` prints after it (UI-913) MUST NOT show as a second row. |
| UI-912 | The header's `⋯` popover MUST offer, for a thread that is not archived, a *Focus of the summary* field (placeholder `What to keep (optional)`) and *Compact context*, which compacts with the field's text like `:compact` (UI-910, UI-911) and closes the popover. |
| UI-913 | **A mode**: when the first word of `:compact`'s arguments names one of omp's modes (`soft`, `remote`, `snapcompact`, in any case), the window MUST send omp's `/compact <mode> [<focus>]` as `thread.prompt` instead of calling `thread.compact`, with the same refusal while the thread works, then show `Compacting the context (<mode>)` as a neutral toast, without a success mark: omp reports the outcome, a skip included, as a command-output card (UI-345) and the compaction notices (UI-911). `snapcompact` with a focus MUST call nothing and show the error `snapcompact takes no focus: it keeps the history as images, without a summary`. The `:` line completes the modes as the first argument; the header's popover offers the focus only. |
