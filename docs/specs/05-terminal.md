# 05 — Terminal

Daemon-owned PTY sessions are data sources for widgets and agent-built interfaces; `useJob` remains the
non-interactive command API. They are independent of omp: there is no omp terminal handoff (D-06, PRT-135).

## Reusable PTY sessions

| ID | Requirement |
| --- | --- |
| TRM-100 | `terminals.start { workspaceId, command, cwd?, cols, rows }` MUST start `sh -c <command>` on a PTY in the workspace folder (or a workspace-relative existing `cwd`) with `TERM=xterm-256color` and `COLORTERM=truecolor`, and return its memory-only session; `terminal/<id>` exposes its state, base64 output chunks and exit status. Absolute or parent-traversing `cwd`, zero dimensions and more than 400 columns or 200 rows MUST be refused. |
| TRM-101 | `terminals.input { terminalId, data }` MUST write the base64-decoded bytes to the PTY, `terminals.resize` MUST resize it, and `terminals.kill` MUST terminate it. Input and output are byte streams: terminal control sequences and non-UTF-8 bytes MUST survive transport. |
| TRM-102 | A terminal session MUST outlive widget unmounts and WebSocket reconnects while the daemon runs. Any authorized client with its id MAY subscribe and interact, and a new subscription MUST receive the bounded snapshot before live events. Sessions are not restored after a daemon restart. |
| TRM-103 | Terminal input MUST NOT be stored in topic state, logs or widget state. Raw output stays in memory only, at most 1 MiB per session, snapshots reporting the number of older bytes dropped. `terminals.screen` returns visible output to its caller only: the daemon MUST NOT add it to activity or persistent state. Frames carry the bytes base64 in JSON. |
| TRM-104 | A terminal started by an agent MUST keep that thread as provenance; cascade stop MUST kill the terminals of the stopped tree, workspace removal its workspace's terminals, daemon shutdown every terminal. Agent activity MAY record terminal calls but MUST replace input bytes with `[redacted]`. |
| TRM-105 | `omfp/sdk` MUST export `useTerminal(command, { cwd?, cols?, rows?, key? })`, which keeps the session id per widget instance and follows `terminal/<id>`. The copyable built-in `omfp:terminal` MUST use xterm.js, forward keyboard input and container resizes, and replay the snapshot without starting a duplicate process. |
| TRM-106 | `terminals.screen { terminalId, afterRevision?, waitMs? }` MUST return the visible screen as plain text, the zero-based cursor and its visibility, dimensions, alternate-screen flag, process status and a revision that advances on output, resize and exit; with `afterRevision` equal to the current one it MAY wait up to 30 s for a change. No scrollback beyond the 400×200 grid; `useTerminal` exposes it as `screen()`. |
| TRM-107 | `omfp:terminal` takes `{ command?, shell?, cwd?, cols?, rows?, key? }`. A non-empty `command` MUST run unchanged and wins over `shell`; else it MUST `exec` the `shell` prop's whitespace-separated words (e.g. `bash -l`), each single-quoted so none is expanded; without a non-blank `shell` it runs `exec "${SHELL:-sh}"`, the daemon environment's shell or `sh`. |
| TRM-108 | **Clipboard keys**: the kit's `TerminalEmulator` MUST copy its selection on Ctrl+Shift+C (Cmd+C on macOS) and paste the clipboard on Ctrl+Shift+V, bracketed when the program enabled it; macOS Cmd+V is left to the platform's paste. Plain Ctrl+C, Ctrl+V and other chords reach the program. A refused clipboard is ignored silently, a paste that completes after the session changed is dropped, and without `navigator.clipboard` copying falls back to `execCommand("copy")`. No copy-on-select. |
| TRM-109 | **Clipboard keys in the omfp window**: a clipboard key the terminal handled MUST reach the window keymap already prevented, so no binding runs for it, and keys sent to the program stop there (plain Ctrl+C never reaches `composer.interrupt`); no default binding uses Ctrl-Shift-c, Ctrl-Shift-v, Meta-c or Meta-v. The Linux desktop window MUST let the page read the clipboard. |
| TRM-110 | The kit's `TerminalEmulator` MUST paint with the active theme's `--omfp-terminal-*` tokens (`terminal-bg`, `-fg`, `-cursor`, `-cursor-accent`, `-selection` and the 16 ANSI colors), which `tokens.css` derives from the color roles, so every built-in theme, skin, color scheme and a roles-only user theme (UI-091) gets them. Built-in themes and skins MUST NOT set terminal tokens. |
| TRM-111 | A change of the effective theme (as `watchTheme` reports it) MUST repaint every open `TerminalEmulator` in place through xterm.js `options.theme`, without re-creating the emulator or restarting its session; a color a widget passes in `options.theme` wins over the token's, at creation and after every change. |
| TRM-112 | Unmounting or re-creating the kit's `TerminalEmulator` (new `cols`, `rows` or `options`) MUST take its emulator off the page at once and dispose it only after xterm.js's pending open work has run, so a terminal closed right after it opened throws nothing. |
