# 09 — Visual design: Crush

The look of omfp, binding for the shell, the kit (`omfp/kit`, UI-093) and the `/kit` gallery: the Crush skin, the
default, and the opt-in boring skin (Skins, UI-794..UI-797). It refines UI-091 (tokens and themes), UI-094 (fonts and
density) and UI-097 (`[ui]` settings); where they disagree on a default, this document wins (D-20). The direction is called **Crush**, after Charm's terminal UI of the same name: monospace chrome
with a few box-drawing glyphs, bold accents, gradients built from the theme's own roles, and motion as the identity —
while long reading stays in a serif face and every effect can be switched off.

## Principles

| ID | Requirement |
| --- | --- |
| UI-120 | omfp's own visual style is **Crush**, implemented in our own CSS (D-10, D-20): no CSS framework, no component library styles. Crush is the **default skin**; the opt-in **boring** skin (UI-794..UI-797) restyles the same components without changing them, and every requirement of this document describes Crush except where a boring row overrides it. Themes change colors and fonts through tokens only (UI-091); they never change layout, glyphs or motion definitions, and any theme works with either skin. |
| UI-121 | **Two families, two jobs.** Text read as text — assistant and user message prose, Markdown, ask option descriptions, the composer's input — uses the prose family (serif). Everything else — chrome (buttons, tabs, rows, titles, labels), metadata (times, counts, paths, branches, token meters), secondary text (thinking text, UI-338) and code (code blocks, inline code, tool arguments and output, diffs, logs, the command line) — uses the code family (monospace). There is no third, sans-serif family: `--omfp-font-ui` is an alias of `--omfp-font-code` (this replaces the sans-serif interface of UI-094). |
| UI-122 | **Glyph vocabulary.** Glyphs are text in the code family, colored by tokens, never images (the brand is the logo, UI-220, not a glyph): `◆` marks an identity or a call for attention — the chat title, the assistant's name in the transcript, the title of an approval or ask card, the mode-line notice, and the *awaiting* thread state; `▸` marks the current choice or a closed disclosure — the user's name in the transcript, the selected tab, the selected command-line completion, a collapsed workspace or thinking block (`▾` once open); `●` is a finished tool call (success or error by color); `○` an idle thread; a braille spinner a running thread or tool (UI-216: the activity frames `⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏` on threads and the header, omp's status frames `⣾⣽⣻⢿⡿⣟⣯⣷` on tool cards); `╭─` opens a titled group — the command menu (`╭─ commands`) and gallery section titles (boxes titled on their border, UI-187, draw that shape with their own border, not with glyphs). `·` separates mode-line segments and `@` prefixes the daemon host. No other decorative glyph is used; Lucide icons (UI-131) cover the rest. |
| UI-123 | **Gradients only where listed** (UI-135): the logo's `π` (UI-221); gradient text on the chat title, the current workspace's name, the assistant's name and gallery titles; gradient fills on the primary button, the selected tab's indicator, the `INSERT` and `COMMAND` mode pills, the command-line prompt, the stream caret, progress fills and meters (the live voice meter included), and the live spectrum's bars (drawn on a canvas, "Live voice" below); gradient hairlines under the chat header and above the mode line; a gradient border on the composer in insert mode; the soft gradient (`--omfp-grad-soft`) as the selection background of rows, files and completions; the 2 px vertical bar of the selected left-column row; the bar over a splitter's hairline on hover, focus and drag (UI-208); the 2 px bar on the top edge of the phone's shown area button (UI-208). Anything else is a flat role color. |
| UI-124 | **Motion is the identity, never a requirement.** Every animation is listed in the motion catalogue (UI-146) with the levels that keep it; at motion `none` (UI-145) the UI is fully static and loses no information: every animated state also has a static form (glyph, color or text). |

## Skins

A skin is the look of the whole UI on top of the tokens: Crush (above, the default) or **boring**, an opt-in calm,
modern look: Linear's chrome, claude.ai's conversation and Notion's typography and whitespace. Boring is one more stylesheet per stylesheet it overrides (the kit's, the
app's and its built-in widgets'); it adds no kit API, no component variant and no second kit.

| ID | Requirement |
| --- | --- |
| UI-794 | **The skin setting.** `[ui] skin` (UI-097, PRT-213) MUST be `crush` (absent: the default) or `boring`; `settings.set` writes it back and every window applies it live (`settings_changed`) as `<html data-skin="crush\|boring">`, beside and independent of `data-theme` (UI-510), `data-density` and `data-motion`, already on the page the daemon serves so the first paint has it (UI-091); `:set skin=…` changes it (UI-097). Agents and widgets read and change it like the other settings (`useSettings`, `useSetSettings`, `settings.set`). |
| UI-795 | **Boring's look**: a classic modern web app (Linear's chrome, claude.ai's conversation, Notion's typography and whitespace), with no terminal-isms. `@omfp/kit/boring.css` (the kit) and the app's `boring.css` (the frame and the built-in widgets) MUST scope every rule under `:root[data-skin="boring"]`, in the layer of what they override, and override only what differs, so whatever they do not cover stays Crush, never unstyled. Using tokens only (UI-091, UI-125): `--omfp-font-ui` and `--omfp-font-prose` are `--omfp-font-sans` (the system sans-serif) and only code (code blocks, inline code, tool arguments, diffs, logs, outputs, paths) keeps the code family, key chips, commands and their arguments taking the interface family; prose at `1rem` with line height 1.6; no uppercase or letter-spaced labels (the mode pill is lowercase). **Neutral chrome**: hover, press, selection and the focus tint are gray steps of `on-surface` (4, 9, 6 and 12 %, so focus stays apart from selection and hover, UI-132), selected rows have no colored bar, the primary button and the `INSERT` pill are inverted (`inverse-surface` / `inverse-on-surface`), secondary buttons outlined, fields with a soft border and, focused, a soft `primary` ring, the `COMMAND` pill `secondary-container`, key chips and counts muted; the accent (`primary`) appears only in the focus bar and ring, links, the selected tab's underline, checks and progress fills and meters, never as a large fill, and the status colors only as small marks (a running or failed tool card's border is the plain card border, an approval or ask card a plain card). The state marks are dots (filled for done, failed, unread and awaiting, a ring for idle), and every `◆` — of an approval or ask card's title, the mode-line notice, the message log, the banners, a widget's error, a file notice — is a small dot in its tone. The mode line reads as an app's status bar: no `·` separators, a small rounded lowercase mode badge, and the `:` line a rounded command field without its `:` prompt. No gradients: every gradient token is one solid color and no rule draws one; gradient text is plain `on-surface` text. **Quiet shapes**: very light borders (`--omfp-rule` is `outline-variant` at 55 %), a subtle neutral shadow on popovers, the left column and cards (tool cards, border boxes, UI-187, drawn as a box with their title in a head row inside it) on `surface-container-low`, code blocks on their gray surface without a frame, inline code `on-surface` on `surface-container`; Crush's radii (about 6 px controls, 10 px cards). **The conversation**: names small and muted without glyphs, the user's message in a `surface-container-high` bubble across the column (0.75rem radius, `s3 s4` padding), the assistant's reply plain text, thinking a muted disclosure without its rule; the composer a 0.75rem rounded box with a light border, `outline` in insert mode; more space between messages (`--omfp-msg-gap` 1.75rem × density). No `╭─` titles, no `▸` before the selected tab or completion, plain muted chevrons (two borders, turned) for every disclosure, a ring spinner for running marks; no shimmer, breathe, bounce, flow, glow or entrance animation (pop-ins, slide-ins, fades, toasts), while the spinners, the indeterminate progress, the stream caret and the transitions stay, under `data-motion` (UI-145). `[ui] density`, `[ui] fonts` (inline on `<html>`) and a user theme still apply. |
| UI-796 | **Glyphs in the stylesheets.** The decorative glyphs of Crush (UI-122) — the `▸`/`▾` disclosures of workspace sections, toggle rows, thinking blocks, cards and disclosures; the `╭─` of box titles (the command menu, the which-key panel, popover dialogs, the gallery's sections); the names' `▸`/`◆` in the transcript; the spinner frames — MUST be generated by CSS (`::before` `content`, keyframes), never written as text in the kit's markup, so a skin can draw its own; Crush shows them exactly as before. |
| UI-797 | **Both skins in the gallery.** `/kit` (UI-173) MUST take `?skin=crush\|boring` and its header's picker MUST link both skins next to the themes and schemes, keeping the other parameters; UI-174's test runs every theme and scheme in both skins, with the same contrast and focus checks, and keeps full-page shots of both (`omfp-kit-<theme>-<scheme>.png`, `omfp-kit-boring-<theme>-<scheme>.png`). |
| UI-984 | **Boring focus on the composer.** In the boring skin a focused field (UI-150) draws a soft accent ring (3 px, `primary` at 22 %) around its box, except the composer's text area (UI-172), which has no box of its own: the composer box draws that ring on `:focus-within`, following its own radius, so the composer shows one focus indication. Crush is unchanged. |

## Tokens

All design tokens live in **one namespace, `--omfp-*`**, next to the Material 3 color roles of UI-091; the lab's
`--ds-*` names are renamed on import (`--ds-fs-sm` → `--omfp-fs-sm`, `--ds-s3` → `--omfp-s3`, `--ds-r-card` →
`--omfp-r-card`, and so on: drop the `ds-` prefix, keep the rest). The kit's earlier ad-hoc tokens
(`--omfp-radius-*`, `--omfp-font-size-*`, `--omfp-row-height`, `--omfp-line-height*`) are replaced by the ones below,
with no aliases. Tokens are declared in the `omfp-tokens` cascade layer; the kit and the shell read them in
`omfp-kit`, so a theme (UI-091) overrides any of them without `!important`.

| ID | Requirement |
| --- | --- |
| UI-125 | Every length, size, color, duration and easing used by the shell or the kit MUST come from the `--omfp-*` tokens listed in this section (or be a `color-mix()` / `calc()` of them); the only literals allowed in component CSS are hairlines and glyph strokes (`1px`, `2px`), `999px` for pills, `50%` for round marks and percentages inside `color-mix()`. |
| UI-126 | **Type scale.** Sizes are in `rem` (UI-094), so the root size (`[ui] font_size`, default **17 px**, UI-144) scales all of them. Values and their size at 17 px are in the type table below; weights are `--omfp-fw-regular: 400`, `--omfp-fw-medium: 600`, `--omfp-fw-strong: 700` (the bundled faces have no 500, UI-141); line heights are `--omfp-lh-ui: 1.4`, `--omfp-lh-prose: 1.5`, `--omfp-lh-code: 1.5`. Labels keep their case (`--omfp-label-case: none`, `--omfp-label-track: 0`). The type scale does not change with density. |
| UI-127 | **Spacing.** `--omfp-unit: 0.25rem`; `--omfp-density` is `1` in compact (the default) and `1.3` in normal (`[ui] density`, UI-097); the steps `--omfp-s1`…`--omfp-s6` and `--omfp-s8` are `unit × n × density` (values in the spacing table below). Paddings, gaps and margins use these steps, or the **text spacing** tokens (text spacing table below): em/ch values for key chips, counts, exit tags, inline code, Markdown flow and glyph gaps, which scale with the text they sit in rather than with density. The scrollbar lane is bounded below by `--omfp-scrollbar-clearance` (layout table): native overlay bars do not shrink with text or density. |
| UI-128 | **Layout sizes** (layout table below): row, control and message-gap heights scale with density; the frame sizes (columns, bars, gutter, reading measure) do not. |
| UI-129 | **Radii and borders.** Radii: `--omfp-r-ctl: 0.375rem` (buttons, fields, selects), `--omfp-r-row: 0.375rem` (rows, menu items), `--omfp-r-chip: 0.3125rem` (chips, badges, key chips, inline code), `--omfp-r-card: 0.625rem` (cards, popovers, dialogs, code blocks, the composer); pills (mode, counts, progress tracks) are `999px`. Borders are `--omfp-bw: 1px`; rules are `--omfp-rule` (`outline-variant` at 80 %) and `--omfp-rule-strong` (`outline-variant`). Borders are **solid** except: the border of approval and ask cards (their labelled rules follow it), queued-message chips, ghost chips, empty-state boxes and gallery size separators, which are **dashed** — dashed means "pending, provisional or placeholder". Accent bars (selected row, user message, code block, thinking text) are `2px` solid. |
| UI-130 | **Surfaces and elevation.** Crush is flat: elevation is shown by surface role and a primary-tinted border, not by grey shadows. `--omfp-app-bg: surface`; `--omfp-side-bg` and `--omfp-bar-bg: surface-container-lowest` (left column, mode line); cards, fields and controls are transparent on their parent (`--omfp-card-bg`, `--omfp-field-bg`, `--omfp-ctl-bg`); `--omfp-code-bg: surface-container-low`; popovers, menus, dialogs and toasts use `--omfp-pop-bg` (`surface-container-low` in light, `surface-container` in dark), `--omfp-pop-border` (primary 45 % into `outline-variant`) and `--omfp-pop-shadow` (a 1 px primary ring at 8 % plus `0 0.75rem 2rem` primary at 14 %) — the only shadow in the UI; key chips sit on `surface-container`. The modal scrim is `scrim` at 36 %. |
| UI-131 | **Icons** are Lucide, stroked with `currentColor`: `--omfp-ic: 0.875rem` (state marks, toolbar icons), `--omfp-ic-sm: 0.8125rem` (inside small controls, fields, rows, menus), `0.75rem` for inline metadata icons, `1.5rem` for empty states; stroke `--omfp-ic-stroke: 2` (empty states 0.8×, checkbox check 3). Where a glyph of UI-122 has the job (state marks, tool status, disclosure), the icon is not shown. |
| UI-132 | **Focus** shows on `:focus-visible` only (fields: `:focus-within`) in two looks, each one shared rule set of the kit; app and widget elements join them with classes (`omfp-focus-item`, with `omfp-focus-item__target` on the child that takes the focus; `omfp-focus-ring`; `omfp-focus-inset`), never rules of their own. *Items you move between* — list, menu and option rows, thread, tree and subagent rows, tool card, workspace section, thinking and disclosure heads, transcript items, the mode-line notice, strip threads — take a soft tint `--omfp-focus-bg` (primary at 12 % over the surface: between hover's 8 % and the selected gradient's 16 % start) and a 2 px `--omfp-focus-bar` (`primary`) on their inline-start edge, both inset shadows over the item's own background and following its radius, so nothing moves; no outline, no glow. On a selected row the focus bar replaces the row's inset gradient bar at full height, so selected and focused differs from selected; a tool card head on the border (UI-187) carries them on its title; a transcript item reaches `s2` into the gutter, so the bar sits beside the message. *Controls and regions* — buttons, select buttons, tabs, checkboxes and radios (on the box), the area bar, and focusable scroll regions (transcript, help list, file view) — keep a quiet ring: `outline: var(--omfp-focus-w) solid var(--omfp-focus-color)` (`1px`, `primary`) at `--omfp-focus-off: 1px`, inside the edge for regions and clipped controls; no glow. *Text fields* take no ring: their border turns `primary` (the composer's field has no border of its own; its box draws it, UI-172). The tint, bar and ring appear without a transition, the same at every motion level. The tokens derive from Material roles only (D-20), so matugen themes follow. Visibility (WCAG 2.4.7) is measured by the `/kit` gallery (UI-174) on `surface`, `surface-container-lowest` and `surface-container-low`: the bar reaches 3:1 against the surface, the tint and the selected tint under it; the tint is at least 3 ΔEok from the unfocused item, and a focused selected row from a selected one; at least 1.5 ΔEok from the hover and selected backgrounds, which the bar tells apart. In forced colors, which drop shadows and tints, items take a 2 px `Highlight` outline inside their edge and the ring is `Highlight`. |
| UI-133 | **Interactive states**, the same for every component: hover `--omfp-hover` (primary at 8 % over the element), pressed `--omfp-press` (primary at 15 %) plus a `translateY(1px)` on buttons; selected `--omfp-sel-bg: var(--omfp-grad-soft)` with `--omfp-sel-fg: on-surface`; disabled `opacity: --omfp-disabled` (`0.42`) with `cursor: not-allowed`, no hover; invalid uses `error`; busy shows a spinner (braille glyph or spinning icon) and keeps the label. Transitions on color, border and transform use `--omfp-dur-1: 110ms`; larger changes `--omfp-dur-2: 220ms`; easing `--omfp-ease: cubic-bezier(0.2, 0.7, 0.2, 1)`. |

## Color

| ID | Requirement |
| --- | --- |
| UI-134 | Every color is a Material 3 role token (UI-091), `--omfp-success` / `--omfp-warning`, or a `color-mix(in oklab, …)` of them; no literal color appears outside theme files. Roles keep their M3 meaning: `primary` is the accent (actions, running, selection, the insert mode), `tertiary` the second accent (user's voice, command mode, inline code, key chips), `secondary-container` neutral counts, `error` failures and destructive actions, `on-surface-variant` secondary text, `outline` hover borders and `outline-variant` rules. |
| UI-135 | **Gradients** are built from roles only: `--omfp-grad-end` = tertiary 68 % mixed with `on-surface`; `--omfp-grad` = `linear-gradient(90deg, primary, tertiary 62%, grad-end)`; `--omfp-grad-loop` (for animated text and progress, drawn at 200 % width) = primary → tertiary 30 % → grad-end 50 % → tertiary 70 % → primary; `--omfp-grad-soft` = primary at 16 % → tertiary at 10 % (selection); the command mode reverses `--omfp-grad`. The end stop pulled toward `on-surface` is the **close-hue fallback**: when a theme's primary and tertiary are close (common with matugen tonal-spot schemes), the gradient still visibly moves in lightness and the text stays readable; no theme needs to define gradient tokens. Gradient text MUST reach WCAG AA 4.5:1 against its background at every stop for the Synth palette and the gallery's matugen theme (checked by the gallery tests, UI-174). |
| UI-136 | **Success and warning** have no M3 role: omfp defines `--omfp-success` / `--omfp-warning` (and `on-` variants) in the base tokens for light and dark, themes MAY override them, and the kit uses them only through `--omfp-ok` = success 85 % into `surface` and `--omfp-warn` = warning 85 % into `surface`, so they take on the theme's surface tint. A matugen theme that does not define them keeps omfp's values. |
| UI-137 | **Status colors.** Thread and tool states: running = `primary`; awaiting the user = `--omfp-warn`; failed = `error`; unread = `primary` (bold title); idle = `outline`. Approval and ask cards use `--omfp-warn` (border at 70 %, `◆` glyph); finished tool calls `--omfp-ok` (●) or `error`; the token meter turns `--omfp-warn` above its threshold; a dirty repo and modified files are `--omfp-warn`, added files `--omfp-ok`, deleted files `error`; exit codes: 0 = `--omfp-ok` on ok 12 %, non-zero = `error` on error 12 %. |
| UI-138 | **Diff, syntax and terminal colors.** Diff: added lines `--omfp-ok` at 12 % background with text = ok 70 % into `on-surface`; removed lines `error` at 11 % with text = error 70 % into `on-surface`; hunk headers `on-surface-variant`. ANSI: red `error`, green `--omfp-ok`, yellow `--omfp-warn`, blue `primary`, magenta `tertiary`, cyan primary 55 % into ok, dim `on-surface-variant`, bold weight 700. Text selection is primary at 28 %. |
| UI-139 | **Built-in palette: Synth** (cyan → indigo), an M3 tonal-spot scheme generated from chosen hues, the default of the built-in themes (UI-510); the built-in theme follows `prefers-color-scheme` (light and dark both MUST be supported) with the manual override of UI-091.
